# Disposable demo test plan

This is a plan for an explicitly approved test session. These steps have not been run. Keep the real n8n draft inactive and its dispatch flags false throughout the first Actions tests.

1. **Create a disposable public repository** such as `patchguard-demo`, using standard GitHub-hosted Ubuntu runners and no secrets, deployments, Vercel connection, environment credentials or production code. Do not use a self-hosted runner. Decide a small Actions/time budget; the workflow has job timeouts and no periodic GitHub trigger.

2. **Add a minimal Next.js npm app** on its default branch using a reviewed, supported Next.js release. Commit package.json and a public-registry npm lockfile v2/v3. Add at least one real `node:test` application test, make `npm test` run it, and ensure `npm run build` passes without secrets. Keep the fixture free of unrelated vulnerabilities so the strict full audit can pass. Leave optional monitoring integrations disconnected.

3. **Copy the implementation**: `.github/workflows/patchguard.yml`, `.github/scripts/patchguard.mjs`, and `tests/patchguard.test.mjs`. The separate n8n runtime tests also require `n8n/runtime-snippets.json` if copied. Review the exact commit SHAs, script contents, repo settings and permissions. Run the local tests and actionlint first. Do not copy credentials. Publishing these files to the demo's default branch is a separate explicit action.

4. **Add one deliberately vulnerable fixture dependency**: in this isolated app, use direct `lodash@4.17.20`, then commit its lockfile. The candidate is `lodash`, `4.17.21`, `GHSA-35jh-r3h4-6jhm`. Recheck the official advisory and npm metadata before using it; do not import or call vulnerable functionality. This advisory/version relationship was checked against GitHub metadata during implementation. Do not deploy this fixture.

5. **Check default-off behavior**: leave the repository variable `PATCHGUARD_TESTS_APPROVED` unset. After approval to run a remote test, manually request PATCHGUARD from the default branch with the fixture inputs. Expect the patch job and PR job to be skipped. Verify there is no patch branch or PR. The workflow_dispatch request itself creates a run record, even when jobs are skipped.

6. **Approve only the disposable test**: inspect Actions settings, permit the pinned official actions, and allow GitHub Actions to create PRs if needed. Set `PATCHGUARD_TESTS_APPROVED=true` on the demo only. No PAT or production secret is needed inside the Actions workflow; it uses short-lived `GITHUB_TOKEN` permissions.

7. **Run negative cases first**, one at a time. Expect validation/check failure and no PR: package `lodash;echo injected`; version `latest`, `^4.17.21` or a major upgrade; a malformed/CVE-only advisory ID; a valid but unrelated GHSA; a transitive-only package; a registry URL dependency; missing tests; a failing build/test; unrelated audit findings; and dispatch from a non-default branch. Do not turn arbitrary malicious text into executable commands. Use harmless literal strings as workflow inputs.

8. **Run the valid fixture** after reviewing the inputs. Expect a read-only patch/check job to switch to `patchguard/<hash>`, perform lockfile resolution, `npm ci`, build, all test scripts and full audit, then upload only the two manifests. The separate publisher must revalidate the artifact and create a draft PR. Inspect logs, job permissions, installed version, integrity and the entire lockfile diff. The default branch must be unchanged. No merge or deployment should occur.

9. **Test refusal and recovery paths**: request the same package/version again and expect an existing-branch refusal rather than a second PR or force push. Concurrent requests for the same target are serialized by Actions. On another fixture, move the default branch while checks are running and expect publisher refusal. Simulate failed audit/build/test with harmless deterministic failures. A branch left after an API failure must be reconciled manually; do not delete it automatically to enable retries.

10. **Exercise n8n read-only against the demo**: in a separately authorized test of this new draft, point Configuration at the disposable repo. Configure a repo-limited GitHub read credential with Dependabot alerts/Contents/Actions read. Enable the dependency graph and Dependabot alerts in the demo, then wait for the fixture alert to appear. Keep `dryRun=true`, all dispatch approvals false and Telegram disabled. Execute manually only after test approval; inspect review output and confirm no Actions POST occurs. Manual n8n runs intentionally never dispatch.

11. **Test failure reporting and Telegram separately**: use synthetic data or a deliberately underprivileged demo read credential to check 403/404/rate-limit and malformed/stale-feed handling. Expect incomplete/unknown results, never an all-clear. If Telegram delivery is approved, use a dedicated test bot/chat and inspect escaped messages. Tokens go only in n8n credentials.

12. **Before testing the scheduled dispatch path**, obtain explicit approval to publish a demo configuration, supply a repo-limited Actions-write credential, enforce serialized n8n execution, and assess the static-data crash/concurrency limitation. Only then set the approval flags and `dryRun=false` on the demo. Verify the first accepted dispatch, persistence across successful scheduled executions, suppression on later scans, and manual reconciliation of timeouts. A no-op/default-off Actions run title can also suppress a target, so use a fresh demo/target or review and clear only authorized test records before this step. This task does not authorize activation.

13. **Finish without merging**: inspect the draft PR and all logs, record results, unset the demo approval variable, unpublish any demo monitoring workflow that was explicitly activated, and revoke test credentials. Delete the disposable repository only with explicit deletion approval. Keep the real project inactive until all required behavior is independently verified.
